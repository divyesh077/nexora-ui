# Project Structure

This document explains the organization of the Nexora UI repository and the responsibilities of its main directories and configuration files.

Understanding the project structure helps contributors develop, maintain, document, and publish reusable components.

## 1. Repository Structure

The Nexora UI repository separates the development application, reusable component source code, generated registry files, and documentation.

```text
nexora-ui/
│
├── .github/
│   └── workflows/
│
├── .vscode/
│   └── settings.json
│
├── docs/
│   ├── getting-started/
│   ├── components/
│   ├── forms/
│   ├── hooks/
│   ├── utilities/
│   ├── guides/
│   └── development/
│
├── public/
│   └── r/
│
├── src/
│   ├── app/
│   │
│   ├── components/
│   │   └── ui/
│   │
│   ├── lib/
│   │
│   └── registry/
│       └── default/
│           ├── button/
│           └── forms/
│               ├── core/
│               ├── fields/
│               ├── actions/
│               └── index.ts
│
├── components.json
├── registry.json
├── package.json
├── pnpm-lock.yaml
├── tsconfig.json
└── README.md
```

The structure above is an architectural overview. Individual directories should contain only the files and categories actually implemented in the repository.

## 2. Main Directories

### `.github/`

Contains GitHub configuration and automation workflows.

Examples:

- Registry deployment workflows.
- Continuous integration.
- Automated validation.

### `.vscode/`

Contains shared Visual Studio Code workspace settings.

Example:

```text
.vscode/
└── settings.json
```

The settings file can configure Tailwind CSS IntelliSense for custom class name properties.

See [Tailwind CSS Class Autocomplete](../guides/tailwind-class-autocomplete.md).

### `docs/`

Contains project documentation.

```text
docs/
├── getting-started/
├── components/
├── forms/
├── hooks/
├── utilities/
├── guides/
└── development/
```

Documentation is maintained separately from reusable component source code.

### `src/app/`

Contains the Next.js application used for developing and testing Nexora UI.

It can include:

- Playground pages.
- Component demonstrations.
- Development-only pages.
- Registry preview pages.

The playground helps verify component behavior before publishing.

### `src/components/ui/`

Contains the UI primitives used by the Nexora UI development application.

Examples include:

- Button
- Input
- Checkbox
- Select
- Field
- Calendar
- Popover

These primitives provide the foundation for higher-level Nexora UI components.

### `src/lib/`

Contains shared utilities and application-level helper functions.

For example:

- Class name utilities.
- Shared formatting functions.
- Common development helpers.

### `src/registry/`

Contains reusable component source code distributed through the Nexora registry.

Example:

```text
src/registry/default/
├── button/
│   └── ...
│
└── forms/
    ├── core/
    │   ├── form.tsx
    │   ├── form-field.tsx
    │   ├── form-field-set.tsx
    │   └── form-types.ts
    │
    ├── fields/
    │   ├── form-input.tsx
    │   ├── form-number-input.tsx
    │   ├── form-textarea.tsx
    │   ├── form-select.tsx
    │   ├── form-checkbox.tsx
    │   ├── form-checkbox-group.tsx
    │   ├── form-radio-group.tsx
    │   ├── form-switch.tsx
    │   ├── form-date-picker.tsx
    │   ├── form-input-group.tsx
    │   └── form-input-group-textarea.tsx
    │
    ├── actions/
    │   ├── form-submit-button.tsx
    │   ├── form-reset-button.tsx
    │   └── form-cancel-button.tsx
    │
    └── index.ts
```

The registry source directory should contain reusable components, not application-specific playground implementations.

Only document and include files that actually exist in the registry.

### `public/r/`

Contains generated registry JSON files.

Example:

```text
public/r/
├── nexora-button.json
└── nexora-forms.json
```

These files are generated by the shadcn registry build process.

They are served through the configured registry hosting provider.

## 3. Important Configuration Files

### `registry.json`

Defines the components distributed by Nexora UI.

A registry item describes:

- Component name.
- Registry type.
- Title and description.
- Dependencies.
- Registry dependencies.
- Source files.
- Installation target paths.

Simplified example:

```json
{
  "$schema": "https://ui.shadcn.com/schema/registry.json",
  "name": "nexora-ui",
  "homepage": "https://divyesh077.github.io/nexora-ui",
  "items": [
    {
      "name": "nexora-button",
      "type": "registry:ui",
      "title": "Nexora Button",
      "description": "Reusable button component.",
      "dependencies": [],
      "registryDependencies": ["button"],
      "files": [
        {
          "path": "src/registry/default/button/index.tsx",
          "type": "registry:ui",
          "target": "components/nexora-ui/button/index.tsx"
        }
      ]
    }
  ]
}
```

The example illustrates the registry structure. Always use the actual paths and item definitions from your repository.

### `components.json`

Configures the shadcn CLI for the Nexora UI project.

It includes settings such as:

- Component style.
- Tailwind configuration.
- Import aliases.
- Registry namespaces.

### `package.json`

Defines:

- Project dependencies.
- Development dependencies.
- PNPM scripts.
- Registry build commands.
- Development and production commands.

### `tsconfig.json`

Defines TypeScript compiler options, module resolution, and import aliases.

## 4. Registry Build Workflow

Nexora UI uses a registry build process to convert component definitions into installable JSON files.

```text
Component Source Files
        |
        v
    registry.json
        |
        v
 Registry Build Command
        |
        v
 Generated Registry JSON
        |
        v
     public/r/
        |
        v
  Registry Hosting
        |
        v
 Consumer Application
```

Build the registry with:

```bash
pnpm dlx shadcn@latest build
```

The generated files are served from the registry hosting location.

## 5. Component Development Workflow

When adding a new reusable component:

1. Create the component source in the appropriate registry category.
2. Implement its TypeScript props and behavior.
3. Reuse existing UI primitives where appropriate.
4. Add the component to the registry manifest.
5. Define its dependencies and installation target.
6. Export it through the appropriate barrel file when needed.
7. Build the registry.
8. Test installation in a separate consumer application.
9. Add documentation for the implemented component.
10. Verify the changes before merging.

## 6. Development Principles

Follow these principles when working in the Nexora UI repository:

- Keep reusable components inside the registry source directory.
- Keep playground code separate from published component code.
- Keep documentation inside `docs/`.
- Use consistent TypeScript interfaces and component naming.
- Reuse shared UI primitives instead of duplicating implementations.
- Keep registry definitions synchronized with source files.
- Test components in a consumer application.
- Document only components that are actually implemented and available.
